# Contracts and API blueprint

**Proposed v1 contract. None of the new endpoints below exist yet.** Implement strict Pydantic models under `backend/app/schemas/planning.py`; generate frontend types from OpenAPI. The prose tables define the intended contract; example JSON is illustrative and does not replace runtime validation.

## Common conventions

- `schema_version`: literal `pulp.planning.v1` for all cross-boundary documents.
- IDs are opaque server-generated strings. Evidence IDs, action IDs and finding IDs are unique within a run and always resolved with that run's ID.
- Timestamps: ISO 8601 UTC with `Z`. Currency: `CAD` only for v1.
- Rates: finite numeric fractions, never percentages. `0.7` means 70% income retained; `0.15` means a 15% increase in household bills.
- Candidate CAD amounts travel as plain decimal strings, such as `"900.00"`; prohibit exponents, commas, currency symbols, NaN, infinity, negatives where disallowed, and excessive precision. Input expenses have at most two fractional digits. Keep existing calculator precision for derived values; round only for presentation.
- Integer fields reject booleans and fractional values. All models forbid extra fields. Validate input lengths and enum values before any model call.
- Display values are generated by the server from numeric evidence, not copied from model prose. Every financial metric carries a unit and evidence reference.
- Scenario IDs distinguish the baseline from alternatives. No alternative can mutate the baseline object.

## IntakeHandoff: candidate data from the separate intake agent

| Field | Type / policy |
|---|---|
| `schema_version` | Literal version |
| `handoff_id` | Client correlation ID; server does not trust it as an authorization token |
| `session_id` | Matches the selected server session |
| `account_id` | Must match server-bound account scope |
| `channel` | `voice` or `text` |
| `utterance_summary` | Relevant summary, maximum 2,000 characters; no raw audio |
| `scenario_candidates` | Six named candidate objects described below |
| `context_proposals` | Candidate `field`, `operation`, `value`, and source reference; not confirmed context |
| `clarifications` | Missing/ambiguous field names and one proposed next question |
| `scenario_approval_receipt_id` | Server receipt or null; agent cannot mint receipts |

Each scenario candidate is `{value, source, source_ref}`. `source` is `user_stated`, `user_edited`, `user_selected_preset`, or `unknown`. A known value needs a transcript-turn/UI-event reference. Unknown values are null; do not silently replace them with defaults. Transcript references remain untrusted until checked against session records.

Required scenario candidates and resolved bounds:

| Name | Meaning | Reviewed-v1 bound |
|---|---|---|
| `income_fraction` | Fraction of typical inflow retained during shock | 0 through 5 |
| `bills_increase` | Fractional change to household bills during shock | -1 through 10 |
| `one_off_cost_cad` | Upfront expense at shock start | 0 through 100,000,000 CAD |
| `shock_start_month` | Zero-based first affected projected interval | 0 through 119 |
| `shock_duration_months` | Number of affected monthly intervals | 1 through 120 |
| `projection_horizon_months` | Entire displayed projection | 1 through 120 |

Require `shock_start_month + shock_duration_months <= projection_horizon_months`. Reviewed v1 does not support a zero-duration shock; use retained income 1, bill increase 0, and an explicit duration for a one-off-only scenario. Existing legacy simulator bounds remain unchanged behind legacy endpoints.

"Income drops 30%" resolves to retained fraction 0.7. "Income becomes 30%" resolves to 0.3. "I might lose income" remains unknown. "A few months" requires clarification. A preset is usable only if its exact assumptions were displayed and selected. The selected hypothetical values do not establish EI eligibility or a personal fact.

## PlanningRequest: server-created trusted input

Never deserialize this directly from untrusted agent output and treat it as trusted. Construct it after resolving the handoff and receipt.

| Field | Meaning |
|---|---|
| `request_id`, `handoff_id`, `session_id`, `account_id` | Server-issued request identity and scope |
| `context_version` | Version of confirmed goals/constraints/preferences used |
| `account_data_version` | Fingerprint of relevant CSV content; not just a filename or mtime |
| `engine_version` | Calculator build/revision identifier |
| `scenario` | Resolved values, baseline scenario ID, CAD, normalized timing |
| `input_sources` | Source references and provenance for each resolved field |
| `assumptions` | Explicit labeled assumptions with approval status |
| `confirmed_context` | Immutable normalized context snapshot; pending proposals excluded |
| `financial_snapshot` | Immutable result of trusted metric computation |
| `simulation` | Seed, path count, engine settings |
| `approval_receipt_id` | Valid receipt binding scenario hash, scope and approval action |
| `input_fingerprint` | Hash of canonical inputs, context/data/engine versions and simulation settings |
| `supersedes_run_id` | Previous run replaced by this request, or null |

Do not include mutable SDK/session objects inside this snapshot. Deep-copy or freeze domain models. Parallel agents cannot overwrite it. Compute a separate run-cache key that also includes model IDs, prompt versions, and orchestration policy; financial evidence caching need not depend on narrative model identity.

## EvidenceRecord

The evidence registry is created only by trusted tool adapters. An agent may cite a record but cannot create one.

Required fields: `evidence_id`, `scenario_id`, `kind`, `tool_name`, `input_fingerprint`, `engine_version`, `units`, `values`, `limitations`. `kind` is `official_shock`, `deterministic_projection`, `simulation`, `strategy_comparison`, `tipping_point`, `confirmed_context`, or `observed_metrics`.

`values` uses a per-tool typed schema, not unrestricted arbitrary JSON. Context evidence uses immutable item IDs and versions. Financial value references use JSON Pointers, for example `/values/monthly_gap_cad`; check that the pointer exists and has an allowed unit/type. Negative balances remain negative; chart rendering must not clip them away.

Official runway evidence includes raw calculation values, display value, capped status, and no-shortfall status. Simulation includes seed, path count, horizon, scenario timing, and model limitations. An assertion about a specific action must cite that action's scenario/strategy evidence rather than the unadjusted baseline.

## DraftPlan and reviews

`DraftPlan`: `draft_id`, `input_fingerprint`, `actions`, `claim_refs`, `assumptions`, `open_questions`. Each action includes an ID, kind, label, relevant context/evidence references, explicit feasibility status, and any required monthly amount from evidence. Supported first-release action kinds: `review_expenses`, `adjust_goal_contribution`, `build_buffer`, `explore_additional_income`, `clarify_constraint`, `monitor_trigger`.

`AgentReview`: `review_id`, `role` (`advocate` or `challenger`), `input_fingerprint`, `draft_id`, `status` (`complete`, `timed_out`, `invalid_output`, `failed`), `findings`, `alternatives_evaluated`.

`ReviewFinding` fields:

- `finding_id`: assigned/normalized by the server.
- `severity`: `blocking`, `material`, or `informational`.
- `issue_code`: stable machine-readable category such as `essential_expense_conflict`, `unconfirmed_capacity`, `insufficient_buffer`, `missing_goal_budget`, `unsupported_claim`.
- `action_id`: affected action, or null for plan-wide findings.
- `description`: concise public-facing issue, not hidden reasoning.
- `evidence_refs`: exact context/calculation references.
- `requested_change`: concrete action the Consultant can take.
- `question`: optional single targeted clarification.

A failed review has no fabricated findings. Report its failure status separately. A review with no findings is still not a numerical proof of correctness.

## PlanningResult

The server assembles the final envelope; the Consultant only supplies a candidate narrative/action selection.

| Field | Contract |
|---|---|
| `schema_version`, `run_id`, `request_id`, `input_fingerprint` | Provenance |
| `status` | `complete`, `incomplete`, `needs_clarification`, `failed`, `cancelled`, `stale` |
| `review_status` | Per-role status; completion cannot be inferred from array length |
| `baseline_scenario_id` | Authoritative baseline |
| `evidence` | Referenced typed records with provenance |
| `metrics` | Label, evidence ID, value pointer, unit, server-generated display value |
| `actions` | Validated final actions, not instructions already executed |
| `findings` | Original review findings, preserved |
| `resolutions` | One per finding: `addressed`, `rejected_with_evidence`, or `unresolved`; final action/evidence refs and explanation |
| `changes` | Server-generated structural diff between draft/final actions and assumptions |
| `questions` | Required clarification, if any |
| `assumptions`, `limitations` | Human-readable, explicitly labeled |
| `context_proposals` | New suggestions for separate user confirmation; no automatic writes |
| `visuals` | Allowlisted component kinds with data references, not code |
| `spoken_summary` | Concise validated explanation for the voice presenter |
| `acceptance` | `eligible` plus machine-readable reasons if ineligible |

`complete` means both reviews completed and final validation passed, not a guarantee that the plan will succeed. Unresolved blocking findings produce `needs_clarification` if user input can resolve them, otherwise `incomplete`. Rejected findings require counter-evidence; the server must reject a resolution consisting only of "the Consultant disagrees."

If a reviewer times out, useful verified calculations may still be displayed as `incomplete`. Acceptance is disabled. Do not replace a missing review with an empty successful review. Preserve cancellation/stale markers on every result fetch.

## Proposed HTTP API

Keep existing endpoints working. Add these under a feature flag:

| Method / path | Behavior |
|---|---|
| `POST /api/agent/intake-handoffs` | Store a bounded candidate handoff in the run/intake store; return candidate ID, missing fields and editable summary. No permanent user memory write. |
| `POST /api/agent/intake-handoffs/{id}/approve` | Explicit UI action with expected candidate version/hash; validate and issue scenario approval receipt. Not an agent tool. |
| `POST /api/agent/plan` | Body `{schema_version, handoff_id, approval_receipt_id, expected_context_version, supersedes_run_id}`. Validate scope/version; return `202` with run ID and URLs. No client-supplied financial snapshot. |
| `GET /api/agent/plan/{run_id}` | Return run status and available final envelope; enforce scope. |
| `GET /api/agent/plan/{run_id}/events` | SSE progress, with monotonically increasing IDs and resumable replay. |
| `POST /api/agent/plan/{run_id}/cancel` | Idempotent cancellation; no personal context change. |
| `POST /api/agent/plan/{run_id}/accept` | Explicit UI action; expected fingerprint/context version and idempotency key; atomically persist accepted plan after revalidation. |

`POST /api/agent/plan` requires an `Idempotency-Key` header. Scope it to the session/account and canonical request body: same key/same body returns the existing run, same key/different body returns 409. Distinct requests with identical inputs may reuse immutable calculation evidence but must not cross account/session boundaries. In the initial local prototype use a bounded single-worker run store; document that idempotency receipts do not survive restart unless persisted.

Clarification response: `422` before run creation for structurally missing/invalid fields; a semantic question discovered during planning is a normal `needs_clarification` result. Resume by updating intake, reapproving changed assumptions, and issuing a new run. Do not keep a live LLM session waiting indefinitely for the user.

Error envelope: `{error: {code, message, field_errors, retryable, correlation_id}}`. Use 404 for unavailable account/run, 409 for stale versions or idempotency conflicts, 422 for invalid input, 429 for admission limits, 503 if reviewed planning is disabled/unavailable. Do not return raw provider exceptions, credential-bearing URLs, or filesystem paths.

## Events

Every event contains `schema_version`, `run_id`, `sequence`, `type`, `at`, `payload`. Event types: `run_started`, `stage_changed`, `review_completed`, `clarification_required`, `result_ready`, `run_incomplete`, `run_failed`, `run_cancelled`, `run_stale`, `heartbeat`.

Events expose real progress, short findings where validated, and result IDs. Never stream raw model deliberation, unvalidated financial claims, or complete private context. The client fetches the authoritative result after `result_ready`; streamed text is not acceptance authority. Bound replay buffers and reject unsupported last-event IDs with an explicit resync instruction.

## Consent and staleness

Three different actions must remain distinct: approve a hypothetical scenario; confirm a personal-context update; accept a reviewed plan. Existing context confirmation can increment the context version and invalidate a reviewed result. Apply context changes first and rerun, or accept a plan based on the unchanged context. Do not silently bundle the actions.

At run completion and acceptance, compare account-data version, context version, input fingerprint, and active scenario approval. Version changes produce stale status and disable acceptance. The accepted-plan transaction should atomically recheck versions and write a single snapshot/receipt. Operational logs may record the attempt; they must not make an unsuccessful acceptance appear applied.
